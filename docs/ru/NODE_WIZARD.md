# Мастер «Создать свою ноду»

Мастер ставит на ваш VDS отдельную выходную ноду OpenFlux и сохраняет готовый
профиль на телефоне. Повторный запуск на том же сервере добавляет ещё одного
пользователя. Каждый канал — отдельная нода со своим документом Яндекса, своим
ключом шифрования и своим экземпляром `openflux-node@<канал>`. Существующие
каналы, Docker, VPN и панели на сервере мастер не трогает.

## Как пользоваться

1. «Профили» → кнопка с терминалом («Создать свою ноду»). Если профилей нет,
   кнопка есть и на пустом экране.
2. **Сервер.** Введите адрес, SSH-порт, логин и пароль или приватный ключ. При
   первом подключении мастер покажет отпечаток ключа сервера. Если он
   изменится позже, мастер предупредит о возможной подмене.
3. **Документ.** «Войти в Яндекс и создать документ»: во встроенном браузере
   войдите в свой аккаунт. Мастер сам создаст папку `openflux` на Диске,
   документ `openflux-<канал>` и откроет редактирование по ссылке. Вместо этого
   можно вставить ссылку на свой пустой документ вида
   `https://docs.yandex.ru/edit/d/…`.
4. **Будут изменения.** Сервер показывает, что именно установит. Для обычного
   пользователя с sudo нужен пароль sudo.
5. **Проверка.** Мастер подключается к новой ноде и открывает сайт через неё.
   Если Яндекс попросит ноду пройти проверку, капча откроется во встроенном
   браузере с адреса сервера.
6. **Готово.** «Сохранить на этом телефоне» и/или «Показать QR» для другого
   устройства. В QR лежит ключ канала.

## Что происходит на сервере

| Путь | Что там |
|---|---|
| `/opt/openflux-node/bin/openflux-<версия>` | ядро OpenFlux из Releases этого репозитория |
| `/etc/openflux-node/<канал>/node.conf` | конфигурация канала (0640) |
| `/etc/openflux-node/<канал>/encryption-key` | ключ канала (0640, `root:openflux-node`) |
| `/var/lib/openflux-node/<канал>/` | cookies транспорта |
| `/etc/systemd/system/openflux-node@.service` | общий шаблон юнита |

Нода работает от системного пользователя `openflux-node` без root, в режиме
`l4`. У неё два транспорта: `vyandex` через документ (приоритет 100) и `direct`
на случайный свободный TCP-порт (приоритет 50). По `direct` нода, получившая
капчу, может передать её в приложение. Если активен ufw или firewalld, мастер
открывает этот порт и закрывает его при удалении канала.

Удалить канал вручную:

```sh
printf 'channel=<канал>\n' > /tmp/c && sudo sh node-install.sh remove /tmp/c
```

## Безопасность

- Цепочка доверия: APK → закреплённый коммит и SHA-256 `deploy/node-install.sh`
  (`provision/pin.go`) → SHA-256 ядра внутри скрипта. Изменённый на GitHub
  файл не будет запущен.
- Пароль SSH, приватный ключ и пароль sudo хранятся только в памяти, пока
  открыт мастер. В аргументах команд их нет. Пароль sudo передаётся через
  stdin, конфигурация канала — через временный файл 0600, который скрипт
  удаляет сразу после чтения.
- Вход в Яндекс остаётся во встроенном браузере. Запросы к Диску выполняются
  со страницы Диска, после создания документа все cookies браузера
  стираются. На сервер уходят только адрес документа, ключ канала и порт.

## Для разработчиков

- `deploy/node-install.sh`: команды `probe`, `plan`, `apply`, `remove`,
  `status`, вывод — одна строка JSON.
- `provision/`: SSH, TOFU, загрузка и проверка скрипта, sudo.
- `mobile/node.go`: API для приложения (`Node*`), включая сквозную проверку
  канала (`NodeVerify`).
- Ядро публикует `.github/workflows/node-release.yml` по тегу `node-v*`. Сборка
  воспроизводимая, и workflow падает, если хеши не совпали со скриптом.
- Изменили скрипт → закоммитьте его, затем обновите `PinnedCommit` и
  `PinnedSHA256` в `provision/pin.go` (`TestPinnedScriptHash` следит за
  хешем). Изменили ядро → новый тег `node-v…`, `CORE_VERSION` и хеши в скрипте.
- Интеграционные тесты против настоящего systemd-хоста:
  `provision.TestInstallOnVDS` и `mobile.TestNodeLive`, переменные окружения
  описаны в самих тестах.
